# Архитектура

Монорепозиторий: бэкенд на Python, клиент на Flutter, общие данные и документация.

```
driver_shifts/
├── backend/            FastAPI + Postgres
├── app/                Flutter-клиент (Android, iOS)
├── data/trips.json     начальные данные из задания
├── docs/               требования, решения, API, план, журнал ИИ
├── docker-compose.yml  API + Postgres одной командой
├── scripts/            smoke.sh — проверка docker compose (make smoke),
│                       check-release-env.sh — адрес API для релиза (make apk)
├── Makefile            up, smoke, gen, gate, apk
└── .github/workflows/  CI и сборка APK
```

```
Flutter-клиент ──HTTP/JSON──▶ FastAPI ──SQL──▶ Postgres
  DayBloc        GET  /days/{date}   summarize()     trips (id PK)
  AddTripBloc    POST /trips         ON CONFLICT
```

## Бэкенд

Модули по доменам, как в [fastapi-best-practices](https://github.com/zhanymkanov/fastapi-best-practices)
(по образцу Netflix Dispatch): у каждого модуля свои `router`, `schemas`, `service`,
`dependencies`. Из Clean Architecture взят один принцип — домен не зависит от фреймворков.
Абстрактных репозиториев, Unit of Work и DI-контейнера нет: у каждого интерфейса была бы одна
реализация, транзакцию задаёт соединение из пула, а внедрение зависимостей уже есть в FastAPI
(`Depends`). Запрос — одна транзакция: `create_trip` делает `INSERT` и, только если вставки
не было, `SELECT`. Старт — тоже одна: блокировка, схема и все начальные данные.

### Стек

| Что | Выбор |
|---|---|
| Язык | Python 3.14 |
| Веб | FastAPI (`fastapi[standard]`), эндпоинты `async def` |
| Модели и настройки | Pydantic v2, `pydantic-settings` |
| База | Postgres 18, асинхронный psycopg 3 с пулом (`psycopg[binary,pool]`, `AsyncConnectionPool`) |
| Зависимости | `uv`, `uv.lock` в репозитории |
| Проверки | `ruff` (линтер и форматтер), `mypy --strict`, `import-linter` |
| Тесты | `pytest`, `hypothesis`, `testcontainers` |
| Запуск | Docker: образ на `uv`, `docker-compose.yml` с `postgres:18` (см. «Docker») |

- **Только актуальные идиомы.** `lifespan` вместо `@app.on_event`, зависимости через
  `Annotated[..., Depends(...)]`, API Pydantic v2 (`model_config`, `model_dump()`,
  `field_validator`). ИИ по старым примерам пишет `class Config`, `.dict()`, `@validator` —
  это ловится на ревью.
- **`ruff` с правилами `DTZ`**: запрещены `datetime` без пояса и `date.today()`. Правило про время
  (D1) проверяет линтер, а не внимательность.
- **Postgres 18 в Docker** хранит данные в `/var/lib/postgresql`, а не в `/var/lib/postgresql/data`,
  как в образах до 18. Том в `docker-compose.yml` монтируется по новому пути.

|---|---|---|---|

| `schemas.py` | нет, см. ниже | Форма данных API: проверка входа (D5), формат выхода, перевод в домен и обратно | Не содержит бизнес-логики |

| `repository.py` | `data/` | SQL, строки базы → `domain.Trip` | Без интерфейса: реализация одна |
| `domain.py` | `domain/` | Модели и чистые функции | Не импортирует FastAPI, Pydantic и psycopg |

### Схемы API и домен

На сервере схемы API (`schemas.py`) и домен (`domain.py`) — разные классы. Это стандарт FastAPI:
официальная документация (раздел «Extra Models») и официальный шаблон full-stack-fastapi-template
заводят отдельные модели для входа, выхода и хранения. Здесь они и правда различаются:

| Модель | Особенность |
|---|---|
| `TripCreate` (вход) | Строгие типы, лишние поля запрещены, время с любым смещением, правила D5 |
| `TripOut` (выход) | Время переведено в пояс водителя (`+05:00`) — это представление, домен о нём не знает |
| `DayReportOut` (выход) | Поля ответа за день: `date`, `timezone`, `summary`, `trips` |
| `domain.Trip` | Время с поясом без формата вывода; только стандартная библиотека |

На клиенте отдельных DTO нет: клиент не владеет контрактом и ничего не хранит, поэтому JSON
разбирается прямо в доменные модели. Сервер контракт определяет, и его форма меняется
независимо от домена.

### Правила

- **Правила проверки D5 — в `TripCreate`.** Через него идут и API, и загрузка `trips.json`:
  правила в одном месте, ошибки `422` указывают на поле.
- **Сервис и репозиторий работают только с `domain`.** Перевод между схемами и доменом —
  в `schemas.py`, вызывают его роутер, `seed.py` и `demo.py`.
- **У каждого эндпоинта `response_model`**: ответ проверяется и совпадает с документацией `/docs`.
- **Защита от дублей — одна атомарная операция в базе.** `insert_if_absent` делает
  `INSERT … ON CONFLICT (id) DO NOTHING RETURNING` и только если строка не вставилась, читает
  сохранённую. Сервис сравнивает её с пришедшей через `same_trip()`. Последовательность
  «прочитать → сравнить → вставить» запрещена: это гонка (D4).
- **Исход `create_trip`** — `Created | Repeated | Conflict`, роутер разбирает его через `match`.
  Аналог sealed `Result` в Dart.
- **Начальные данные** идут через `TripCreate` и тот же `create_trip`: те же проверки, и повторный
  запуск не плодит дубли.
- **Зависимости проверяет CI** — два контракта `import-linter`:
  - слои `router | seed | demo` → `schemas | dependencies` → `service` → `repository` → `domain`;
    нижний слой не импортирует верхний;
  - `domain` не импортирует `fastapi`, `pydantic` и `psycopg`.

Тесты из `tests/unit/` идут без базы. Тесты из `tests/integration/` — на настоящем Postgres 18,
который поднимает `testcontainers`. `uv run pytest` требует только Docker и одинаково работает
локально и в CI. На моках гонку не воспроизвести. Тесты API с самого начала идут через
асинхронный клиент `httpx.AsyncClient` — на нём же тест 20 одновременных запросов.

### Docker

`make up` — это `docker compose up --build`: Postgres и API с поездками из `data/trips.json`,
API на `http://localhost:8000` (документация — `/docs`).

- **Образ** (`backend/Dockerfile`) собирается в две стадии. В первой `uv sync --locked --no-dev`
  ставит зависимости из `uv.lock`. Во второй остаются Python, `.venv`, код и `data/trips.json`,
  а `uv` в итоговый образ не попадает. Сборка идёт из корня репозитория, потому что там лежит
  `data/trips.json`; `.dockerignore` пропускает в контекст только нужные файлы. Путь к файлу
  задаёт `TRIPS_FILE`. Процесс работает не от root.
- **Пояса.** `Asia/Almaty` берётся только из пакета `tzdata`, версия закреплена в `uv.lock`.
  `PYTHONTZPATH=""` отключает базу поясов базового образа: иначе версия базы зависела бы от того,
  когда собран образ Python. Обновление — `uv lock --upgrade-package tzdata`. С устаревшей базой
  (`tzdata` 2023.4) `Asia/Almaty` на 2026-10-01 даёт `+06:00` (D1).
- **Порядок старта.** У `db` healthcheck — `pg_isready` по TCP. При первом запуске entrypoint
  поднимает временный сервер только на сокете, и проверка через сокет прошла бы слишком рано.
  `api` ждёт `depends_on: condition: service_healthy`. У `api` свой healthcheck на
  `/openapi.json`: uvicorn отвечает только после lifespan, то есть после схемы и начальных данных,
  поэтому `docker compose up --wait` возвращается, когда API готов.
- **Том** `pgdata` смонтирован в `/var/lib/postgresql` (Postgres 18). Порт базы наружу не открыт.
- **Процессы.** Один процесс `fastapi run`: эндпоинты асинхронные, нагрузка — один водитель.
  `WEB_CONCURRENCY` меняет число процессов без пересборки. У каждого процесса свой пул до
  `DATABASE_POOL_MAX_SIZE` (10) соединений, поэтому процессы × 10 должны укладываться
  в `max_connections` Postgres (100, из них 3 зарезервированы). Одновременный старт нескольких
  процессов безопасен благодаря `pg_advisory_xact_lock`. Порт меняется переменной `PORT`.
- **Проверка** — `make smoke` (`scripts/smoke.sh`), она же job в CI. Стек с пустого тома →
  смещение `Asia/Almaty` внутри контейнера → 01.10 совпадает с заданием → новая поездка →
  `down` и снова `up` на том же томе → 01.10 без дублей, новая поездка на месте, вчерашний
  демо-день тот же, что до перезапуска (D13). До и после —
  `docker compose down --volumes`.
- **`postgres:18` и `postgres:18-alpine`.** Compose берёт Debian-образ, тесты (`testcontainers`) —
  alpine: он меньше. Разница — glibc и musl, у них разная сортировка текста по `en_US.utf8`.
  Текст у нас сортируется только вторым ключом: `id` при одинаковом начале поездки.

## Клиент

Feature-first, Clean Architecture, BLoC — в объёме, который нужен этой задаче.

### Сверка с рекомендациями Flutter

Официальные рекомендации по архитектуре (docs.flutter.dev/app-architecture) и пример compass_app
из `flutter/samples`. Уровни: strong — делать всегда, recommend — советуют, conditional — только
при условиях.

| Рекомендация | Уровень | У нас |
|---|---|---|
| Слои данных и интерфейса, паттерн «репозиторий» | strong | `data/`, `presentation/` |
| Абстрактные репозитории | strong | `TripsRepository` и его реализация |
| Без логики в виджетах, однонаправленный поток данных | strong | BLoC — в терминах Flutter он играет роль ViewModel |
| Неизменяемые модели, freezed | strong / recommend | ✓ |
| Внедрение зависимостей | strong | get_it + injectable |
| Фейки в тестах; компоненты по отдельности и вместе | strong | фейковый репозиторий, тесты блоков, тест фичи целиком |
| Доменный слой с use cases | conditional: «в большинстве приложений use cases добавляют лишнюю нагрузку» | без use cases |
| Отдельные модели API и домена | conditional: «для больших приложений» | без DTO; исключение — тела ошибок |
| go_router для навигации | recommend | навигации нет: один экран и нижний лист |

Сознательные отличия от compass_app: интерфейс репозитория лежит в `domain/`, как в Clean

и `view_models/`.

### Правила

- **Ошибки.** Репозиторий оборачивает вызовы в `handleError` из `HandleErrorMixin` и возвращает
  `Result<T>`. `Failure` — sealed: `ConnectionFailure`, `TimeoutFailure`, `ValidationFailure`
  (ошибки по полям из `422`), `ConflictFailure` (`409`), `BadResponseFailure`,
  `UnexpectedFailure`. `isTransient` решает, можно ли повторить запрос (D7). Тела ошибок `422`
  и `409` разбираются в `core/network/api_error.dart`: это модели API, в домен они не попадают.
  Всё, что зависит от Dio, лежит в `core/network/`, и миксин тоже
  (`core/network/handle_error_mixin.dart`). Поэтому `Failure` и `Result` не импортируют Dio,
  и домен от него не зависит.
- **Модели.** JSON разбирается прямо в доменные модели (`freezed` + `json_serializable`),
  отдельных DTO-копий нет (почему на сервере иначе — в разделе «Схемы API и домен»).
  `field_rename: snake` задан один раз в `build.yaml`, поэтому `@JsonKey(name:)` на каждом поле
  не нужен.
- **Новая поездка — сразу полный `Trip`.** `id` генерирует клиент, поэтому отдельные параметры
  (`params/new_trip`) не нужны: репозиторий принимает `addTrip(Trip)`. Черновик формы
  с незаполненными полями — это состояние блока, а не домен.
- **Состояние блоков — один `freezed`-класс со `status`.** Документация bloc (раздел «Modeling
  State») советует такой вариант, когда нужно показать ошибку, не теряя прошлые данные.
  Sealed-подклассы — только для взаимоисключающих состояний.
  - `DayState`: `date`, `status` (`loading`, `success`, `failure`), `report`, `failure`. При смене
    дня `report` сбрасывается. При обновлении того же дня он остаётся на экране, пока идёт запрос,
    и не пропадает при ошибке.
  - `AddTripState`: `tripId` (UUIDv7, создаётся при открытии формы), `draft` — заполненная
    наполовину форма (`TripDraft`: дни и время начала и окончания, сумма, комиссия, способ
    оплаты), `status` (`editing`, `submitting`, `success`, `failure`), `fieldErrors` (поле →
    причина), `failure` последней отправки и `trip` — последняя отправленная поездка, после
    успеха — сохранённая. `tripId` переживает повторные отправки (D7). Ошибка поля пропадает,
    когда меняют это поле или поле, от которого она зависит: «окончание раньше начала» — при
    смене начала, «комиссия больше суммы» — при смене суммы. `unconfirmedTrip` — отправленная
    поездка, если она могла сохраниться: после временной ошибки или `409`.
- **События и конкурентность.** События — в прошедшем времени, по соглашению bloc: `DayStarted`,
  `DayChanged`, `DayRefreshRequested`, `TripSubmitted`. После каждого `await` —
  `if (isClosed || emit.isDone) return;`.
  - `DayBloc`: все события дня — в одном обработчике с `restartable()`. Новый запрос отменяет
    устаревший, даже если старый был обновлением, а новый — сменой дня, поэтому экран
    не покажет данные чужого дня.
  - Экран отправляет `DayChanged`, только когда страница дня встала на место, а не на каждый
    кадр перетаскивания. Пролистанные на ходу дни не загружаются вовсе.
  - `AddTripBloc`: `droppable()` на отправку; повтор только при `isTransient` и с тем же `tripId`.
    Пока поездка отправляется, правки формы игнорируются: после ошибки форма показывает ровно то,
    что ушло на сервер. Новая отправка после `422` или временной ошибки, в том числе после
    правки, идёт с тем же `tripId`: если поездка уже сохранилась по запросу с потерянным ответом,
    сервер ответит `409`, а не создаст вторую. `409` завершает форму (`conflicted`): правки
    и отправки больше не принимаются, повтор того же `id` снова дал бы `409`.
- **Блоки не знают друг о друге.** Документация bloc: зависимостей между блоками одного слоя
  избегать. Экран создаёт `AddTripBloc` при каждом открытии формы из `TripsRepository`
  и `DriverClock`, которые корень отдаёт через `RepositoryProvider`, и закрывает его после
  закрытия листа. После успешного сохранения `BlocListener<AddTripBloc>` закрывает форму
  и сообщает `DayBloc` о дне поездки. `DayRefreshRequested` без параметров заново загружает
  показанный день, поэтому поездка в показанном дне — это `DayRefreshRequested`, в другом —
  переход на страницу `clock.dayOf(trip.start)`, а `DayChanged` уходит, когда она встала на
  место. То же правило экран применяет к `unconfirmedTrip`, когда лист закрыли после
  временной ошибки или `409` — крестиком, свайпом вниз или «назад»: водитель видит,
  сохранилась ли поездка, прежде чем вводить её снова. Новая форма — новый `id`, поэтому дубль в этом случае всё же
  возможен, если водитель введёт поездку ещё раз; это ограничение записано в D7.
  `DayChanged` принимает только календарную дату `DateTime.utc(y, m, d)` (это проверяет
  `assert`), а `DriverClock.dayOf` даёт день момента по Алматы: 02.10 00:30+05:00 — это 02.10,
  хотя в UTC ещё 01.10 (D1).
- **freezed 3+.** Класс объявляется с `abstract` (один конструктор) или `sealed` (несколько).
  В виджетах — `switch` с сопоставлением с образцом, а не `when` / `maybeWhen`.
- **Время.** `DateTime.parse` теряет смещение, а `toLocal()` переводит в пояс телефона.
  Время поездок и «сегодня» показываются в `Asia/Almaty` через пакет `timezone`. Экран
  пересчитывает «сегодня», когда приложение возвращается из фона и в полночь по Алматы.
  Показанный день при этом сам не меняется: водитель мог смотреть прошлую смену.
- **Тесты.**
  - Фейки вида `extends Fake implements TripsRepository`, а не моки.
  - Тесты блоков проверяют порядок состояний.
  - Smoke-тест DI: граф зависимостей собирается.
  - Тест фичи целиком: экран с настоящими блоками и фейковым репозиторием — открыть день →
    добавить поездку → увидеть обновлённую сводку.

### Окружения

Почему так — [D12](decisions.md#d12-адрес-api-и-демо-бэкенд-в-интернете).

Адрес API задаётся при сборке: `--dart-define-from-file=env/<файл>.json` с ключом `API_BASE_URL`.
В коде его читает `core/config/env.dart`.

| Файл | Адрес | Для чего |
|---|---|---|
| `env/android-emulator.json` | `http://10.0.2.2:8000` | Эмулятор Android, бэкенд из `make up` |
| `env/ios-simulator.json` | `http://localhost:8000` | Симулятор iOS |
| `env/local.json` (в `.gitignore`, пример — `local.example.json`) | `http://<IP компьютера>:8000` | Телефон в той же сети |
| `env/prod.json` | `https://…` | APK в Releases и демо |

Локальный `http` по умолчанию блокируют обе платформы. На Android он разрешён только в
отладочной сборке (`usesCleartextTraffic` в `src/debug/AndroidManifest.xml`), на iOS — только
для локальной сети (`NSAllowsLocalNetworking` в `Info.plist`). Сборка для Releases ходит по HTTPS.

**Деплой бэкенда.** Render по [render.yaml](../render.yaml) (Blueprint): веб-сервис собирается
из `backend/Dockerfile` с корнем репозитория как контекстом, `DATABASE_URL` берётся из базы
`driver-shifts-db` (Postgres 18), регион Франкфурт, проверка здоровья — `/openapi.json`. При старте
бэкенд сам применяет схему и загружает `data/trips.json` (D10) и демо-поездки за 14 дней
(`DEMO_DAYS`, D13), отдельной миграции нет. После каждого
слияния в `main` Render пересобирает сервис. Тариф бесплатный, у него две оговорки:
- сервис засыпает после 15 минут без запросов, первый запрос после этого идёт около минуты
  (D12, «Риски»): приложение покажет ошибку с «Повторить», повтор через минуту проходит;
- бесплатная база живёт 30 дней с создания, потом её нужно перевести на платный тариф или
  создать заново — данные из `trips.json` загрузятся сами.

**Релиз.** APK для GitHub Releases собирает `.github/workflows/release.yml` по тегу `v*`.
Сначала `scripts/check-release-env.sh` проверяет `env/prod.json`: файл есть, `API_BASE_URL`
начинается с `https://`. Иначе workflow падает на первом шаге и пишет, чего не хватает: APK
с неверным адресом открылся бы и не загрузил ни одного дня. Затем `make apk` собирает
`flutter build apk --release --dart-define-from-file=env/prod.json`, и в релиз попадают
`driver-shifts-<тег>.apk` и `driver-shifts-<тег>.apk.sha256`. Сборка, в которой работает сторонний
код из pub и Gradle, идёт с правами только на чтение; `contents: write` есть только у задания,
которое создаёт релиз.

Как выпустить:

1. Добавить `app/env/prod.json` с адресом бэкенда — `{"API_BASE_URL": "https://…"}` — и влить
   в `main`.
2. Проверить сборку локально: `make apk` (APK — `app/build/app/outputs/flutter-apk/app-release.apk`).
   Другой файл окружения — `make apk RELEASE_ENV=<путь>`, проверка та же.
3. Поставить тег на коммит из `main`, где уже есть `env/prod.json`:
   `git tag v0.1.0 && git push origin v0.1.0`.

Версия APK берётся из тега: `v0.1.0` даёт `versionName` 0.1.0, а `versionCode` — номер запуска
workflow (`github.run_number`), который растёт с каждым релизом. Тег не вида `vX.Y.Z` останавливает
сборку на первом шаге. Локальный `make apk` берёт версию из `pubspec.yaml`.

Подпись — отладочный ключ из шаблона Flutter (`signingConfig = signingConfigs.getByName("debug")`
в `android/app/build.gradle.kts`): APK ставится на телефон, для демо этого достаточно, но
в Google Play его не примут. Отладочный ключ хранится на машине сборки, а машина в CI каждый раз
новая, поэтому новая версия может не встать поверх старой — тогда старую нужно удалить.

### Интерфейс

Почему так — [D11](decisions.md#d11-интерфейс-material-3-и-адаптивное-поведение). Макеты,
цвета, размеры и озвучка всех состояний — в [design/README.md](design/README.md) (handoff из
Claude Design, направление 1a «Сгруппированный список»); если код и макет расходятся, верен
этот README, а отступления перечислены в описании PR 12.

Отступления от handoff в PR 13 — по решению пользователя после проверки редизайна на
устройстве. Handoff (раздел 8) описывает самописный свайп: содержимое едет за пальцем и меняет
день после 30% ширины, а новый день въезжает через `AnimatedSwitcher` со сдвигом 24 dp. Такая
смена дня не похожа на вкладки: соседнего дня не видно, а жест не доводится физикой. Теперь дни —
страницы. Handoff (раздел 5) также оставлял лист формы с `enableDrag: false`, а обычный нижний
лист на iOS и Android смахивается вниз. Теперь лист смахивается и показывает ручку, но не во
время отправки (D7). Сам README handoff не меняется.

**Тема.** Material 3, `ColorScheme.fromSeed(#00AFCA)` (tonalSpot), светлая и тёмная версии
по системной настройке, шрифты системные: SF Pro на iOS, Roboto на Android. Всё лежит
в `core/theme/`:

- `app_theme.dart` — `ThemeData`: фон экрана и карточки разных ролей (светлая — фон
  `surfaceContainer`, карточки `surfaceContainerLowest`; тёмная — `surface`
  и `surfaceContainerHigh`), карточки без теней с радиусом 16, шапка 48 dp, основная кнопка
  56 dp с радиусом 16 (в тёмной теме — `primaryContainer`), нижний лист с радиусом 28
  и затемнением 32%, на iOS — без ripple, нажатие затемняет на 8%;
- `payment_colors.dart` — `ThemeExtension` `PaymentColors`: кружки наличных и карты из палитр
  `material_color_utilities` (оттенки 150 и 260, тона 90/30, в тёмной теме наоборот). Hex
  из макетов — ожидаемые значения в тесте темы;
- `app_icons.dart` — `AppIcons.of(context)`: `CupertinoIcons` на iOS, Material Icons на
  Android. Наличные и карта — `Icons.payments_rounded` и `Icons.credit_card_rounded`
  на обеих платформах;
- токены: `Spacing`, `Radii`, `Sizes` (высоты строк, кружки, значки), `Motion` (длительности
  и кривая анимаций), `Opacities`, `AppTextStyles` (цифры одинаковой ширины, жирность);
- `text_scale.dart` — `TextScale.isLarge` (масштаб от 1,5) и `TextScale.headline` (не больше
  1,6) для крупного текста; `text_measure.dart` — ширина текста при текущем масштабе, по ней
  раскладки решают, помещаются ли тексты рядом;
- `AppTheme.withPlatformPress` — затемнение 8% при нажатии на iOS и для кнопок со своим
  стилем: `styleFrom(foregroundColor: …)` строит свой оттенок нажатия.

Виджеты берут цвета, шрифты, отступы и размеры только из темы и токенов, без литералов
`Color(0x…)` и чисел на месте. Красный — только для ошибок, цвет оплаты — только в кружках.

**Экран дня.**

- Шапка: «Дневник смен» по центру, справа текстовая кнопка «Сегодня». На сегодняшнем дне она
  гаснет за 150 мс, но место сохраняет, чтобы заголовок не сдвигался.
- Ряд дня: стрелки ‹ › и подпись дня — кнопка со стрелкой раскрытия, она открывает выбор даты.
  «Сегодня, 7 октября», «Вчера, …», «Завтра, …», иначе день недели.
- Сводка — карточка: строки «Выручка» и «Комиссия», крупно «На руки» с числом поездок, под ней
  наличные и карта в две колонки с кружками оплаты. Пустой день сводку не показывает.
- Ниже заголовок «Поездки» и карточка-список (`SliverMainAxisGroup`, `DecoratedSliver`,
  `SliverList.separated`). Строка поездки: кружок оплаты, время «08:10 – 08:32», под ним
  «Карта · комиссия 360 ₸», справа сумма. Если по календарю Алматы поездка кончается в другой
  день, рядом со временем плашка «+1 день» («+2 дня» и так далее: `DriverClock.daysLater`
  сравнивает `dayOf` начала и конца; это сравнение дат, а не расчёт денег). Если время,
  способ оплаты с комиссией и сумма не помещаются в строку без разрыва слова, строка
  складывается, как при крупном шрифте: сумма уходит под время.
- Внизу — `Scaffold.bottomNavigationBar` с кнопкой «Добавить поездку». Пока под ней есть
  поездки, над панелью видна линия. Список кончается на 16 dp выше панели.
- Суммы печатаются цифрами одинаковой ширины и через `MoneyText`: одной строкой
  в `FittedBox`. Сумма, которая шире своей строки, уменьшается целиком; поэтому у `MoneyText`
  всегда ограниченная ширина. «Комиссия N ₸» в строке поездки тоже не рвётся, а уменьшается.
- Наличные и карта стоят в две колонки, пока подпись помещается в половину карточки;
  иначе — в столбец.
- Состояния: скелетон — только если загрузка дольше 300 мс, полосы пульсируют; пустой день —
  кружок со значком и «В этот день поездок нет»; ошибка первой загрузки — кружок «нет связи»,
  «Не удалось загрузить поездки», причина и «Повторить». Если не удалось обновить показанный
  день, он остаётся на экране, а сверху появляется плашка с причиной и «Повторить».
- Дни листаются как вкладки. Каждый день — страница (`DayPages`: горизонтальный `Scrollable`
  с `PageScrollPhysics`). Соседний день лежит рядом и тянется за пальцем, отпущенную страницу
  доводит до места физика прокрутки, как в `PageView` и `TabBarView`. Подпись дня следует за
  страницей, которая занимает больше половины экрана, а загрузка начинается, только когда
  страница встала на место. Стрелки, выбор даты, «Сегодня» и переход к дню сохранённой поездки
  листают той же анимацией за 300 мс. Далёкий день сначала подставляется рядом с текущим, как
  в `TabBarView`, и въезжает на одну страницу: промежуточные дни не мелькают и не загружаются.
  Прыжок без анимации был бы проще, но тогда «Сегодня» после пяти дней назад вело бы себя иначе,
  чем стрелка. Блок хранит один отчёт, поэтому соседняя страница — скелетон, пока день
  не загрузится (без кэша отчётов по дням). Свайп исключён из семантики, действия есть
  у стрелок, а новый день диктор слышит из подписи дня (`liveRegion`).
- Анимации: плашки ошибок раскрываются за 200 мс. Сохранённая поездка подсвечена и за 1,2 с
  гаснет до цвета карточки. Если анимации выключены в системе, стрелки и выбор даты меняют
  страницу сразу, а скелетон не пульсирует.

**Форма поездки** (нижний лист). Открывается кнопкой «Добавить поездку».

- Лист смахивается вниз, как обычный нижний лист на iOS и Android, и сверху у него ручка
  (32 × 4, `onSurfaceVariant`). Заполненные поля при этом теряются, как и при крестике.
  Для диктора ручка — кнопка «Закрыть», как у ручки Flutter. Ручка своя: жест листа Flutter
  закрывает маршрут через `Navigator.pop` мимо `PopScope`, и так же делает касание диктора по
  его ручке. Пока поездка отправляется, лист сам забирает вертикальные жесты, и жест маршрута
  не начинается.
- Шапка «Новая поездка» с крестиком. Поля сгруппированы в две карточки: «Начало» и «Окончание»
  (у каждого кнопки дня и времени), «Сумма» и «Комиссия» (значение справа, пустое поле —
  только «₸»: серый «0» выглядел как введённое значение; линия фокуса 2 dp). Ниже «Способ
  оплаты» — `SegmentedButton` во всю ширину со значками. Выбранный способ залит
  `primaryContainer`, и вместо его значка стоит галочка: бледный `secondaryContainer`
  на симуляторе почти не отличался от невыбранного.
- День по умолчанию — показанный. Если это сегодня, в форме уже поездка на 20 минут,
  которая кончается в текущую минуту по Алматы: водитель чаще вносит поездку, которая только
  что кончилась. Если начало ушло бы во вчера (до 00:20), время пустое. В другой день время
  пустое, а выбор окончания при выбранном начале открывается на 15 минут позже начала, а не
  на «сейчас»: иначе, приняв оба времени, водитель получал бы окончание, равное началу.
- Смена начала (дня или времени) сдвигает окончание на столько же, если у поездки была
  длительность больше нуля, как в Календаре iOS: 18:05 – 18:25 с началом 18:08 — это
  18:08 – 18:28. Если время окончания, которое водитель выбрал сам, раньше времени начала,
  окончание переходит на следующий день (D2), и у «Окончания» появляется «+1 день» (по тому же
  правилу, что в списке: «+2 дня», если день окончания выбран на два дня позже): 23:50 – 00:20
  вводится без выбора дня. Когда водитель выбрал день окончания сам, он больше не меняется
  сам. Одинаковое время начала и окончания остаётся в одном дне и даёт ошибку «Окончание
  должно быть позже начала», а не поездку на 24 часа; сдвинутое потом начало окончание не
  трогает, поэтому 18:05 – 18:05 с началом 18:08 — ошибка, а не поездка на 23 ч 57 мин.
  Время 24-часовое, как в списке поездок.
- Сумма и комиссия — цифровая клавиатура, только целые тенге, разделитель разрядов как
  в сводке (D3). Правка, в которой есть что-то кроме цифр и пробелов (`2400,50`, `-150`,
  буква), не принимается: в поле остаётся прежнее значение. Сумма не меняется без ведома
  водителя — ни округлением, ни выброшенной запятой.
- У цифровой клавиатуры iOS нет кнопки «Готово». Клавиатуру убирает любое касание мимо поля:
  заголовок листа, «Наличные / Карта», «Сохранить», прокрутка, начатая не на поле. Перед
  выбором дня или времени поле теряет фокус, поэтому после выбора клавиатура не появляется
  снова — и когда кнопку нажали пальцем, и когда её включил диктор. Так же на Android.
- Кнопка внизу листа закреплена: поля прокручиваются над ней, а при открытой клавиатуре она
  стоит прямо над клавиатурой. Плашка с причиной неудачи — в конце полей, над кнопкой.
  В закреплённой части она при крупном шрифте забрала бы место у поля, в которое водитель
  вводит сумму, а на маленьком телефоне в горизонтальной ориентации не поместилась бы над
  клавиатурой.
- Ошибки проверки — под своей строкой, со значком: локальные после нажатия «Сохранить»,
  ошибки из `422` после ответа. Подпись поля с ошибкой красная. Текст выбирается по полю
  и `type` ([api.md](api.md#422)), для незнакомого `type` — общий. Локальная проверка
  плашки не показывает: ошибки уже стоят у полей, а общая плашка оставалась и после того, как
  водитель их исправил. Над кнопкой — плашка с причиной неудачной отправки: «Проверьте данные
  поездки.» на `422` (до следующей правки формы), нет связи, «Эта поездка уже
  сохранена — с данными первой отправки. Проверьте её в списке.» на `409`. Текст `409` свой:
  в тексте сервера есть `id` поездки, и диктор прочитал бы UUID вслух. Каждая отклонённая
  отправка даёт заметную вибрацию, даже с теми же ошибками.
- После временной ошибки кнопка называется «Повторить» и отправляет ту же поездку с тем же
  `id`. После `422` — «Сохранить». После `409` поля выключены, а кнопка — «Закрыть».
- Пока поездка отправляется, поля бледнеют до 50% и выключены, на кнопке индикатор и «Поездка
  сохраняется», а лист нельзя закрыть ни кнопкой, ни свайпом вниз, ни ручкой, ни жестом
  «назад», ни нажатием мимо листа:
  ответ должен дойти до блока, иначе сохранённая поездка не появилась бы в списке и водитель
  добавил бы её второй раз. Цена — при плохой связи лист заблокирован до таймаутов Dio: 10 с
  на соединение, 10 с на отправку и 30 с на ответ, то есть до ~50 с. Отменить запрос нельзя:
  сервер мог уже сохранить поездку, а ответ всё равно нужен.

**Крупный текст.** Порог — `TextScale.isLarge`: масштаб 1,5 и больше. Тогда шапка
«Дневник смен» скрыта, день занимает свою строку, а под ним стрелки и «Сегодня»; наличные
и карта — в столбец; в строке поездки сумма уходит под время и способ оплаты, кружок
уменьшается до 32 dp и встаёт в строку способа оплаты, «+1 день» — своей строкой;
разделители поездок — с отступом 16; у кнопки «Добавить поездку» нет «+». В форме подписи
встают над значениями, кнопки оплаты — в столбец (и раньше, если «Наличные» не помещается
в половину строки). Ограничены 160% только подпись дня и «На руки» (`TextScale.headline`),
остальной текст растёт без ограничений. Суммы уменьшаются целиком в `FittedBox`. Наличные
и карта и строка поездки складываются и раньше 1,5, если тексты не помещаются рядом без
разрыва слова (`TextMeasure`).

**Поведение на iOS и Android.** Один интерфейс, платформенные различия — там, где их замечает
пользователь:

| Что | iOS | Android |
|---|---|---|
| Отклик на нажатие | без ripple, затемнение 8% | InkSparkle |
| Значки | `CupertinoIcons` (кроме наличных и карты) | Material Icons |
| Выбор даты и времени | `CupertinoDatePicker` в нижнем листе с именем поля | `showDatePicker`, `showTimePicker` |
| Диалоги | `showAdaptiveDialog` + `AlertDialog.adaptive` | то же |
| Индикаторы | `CircularProgressIndicator.adaptive`, `RefreshIndicator.adaptive` | то же |
| Свайп назад, пружинящая прокрутка | Flutter делает сам | — |

Лёгкая вибрация (`HapticFeedback`) — при смене дня и после сохранения поездки; заметная —
когда отправка формы не удалась.

**Доступность.** Экран дня и форма проверяются при масштабе шрифта 200% на телефоне 320 dp:
текст переносится, ничего не обрезается. Порядок и тексты для экранного диктора — в
[design/README.md](design/README.md), раздел 9. Суммы читаются словами («Выручка 3 900 тенге»,
«На руки 3 315 тенге, 2 поездки»), поездка — одной фразой: «С 23:50 до 00:20 следующего дня,
карта, 4 600 тенге, комиссия 690 тенге»; плашка «+1 день» диктору не видна. «Дневник смен»,
подпись дня и «Поездки» — заголовки. Области нажатия — не меньше 48 × 48. Ошибки, загрузка
и новый день после смены объявляются диктору сами (`Semantics(liveRegion: true)`), без
переноса фокуса. Сохранённую поездку VoiceOver объявляет: «Поездка добавлена».

Исключение — календарь `showDatePicker`: он ограничен масштабом 130%, как собственный
календарь диапазона во Flutter. При 200% Flutter обрезает двузначные числа дней. При 130%
на телефоне шириной 320 dp кнопка месяца всё равно сокращается до «октябрь 202…», а сетка дней
видна целиком. Циферблат `showTimePicker` ограничен теми же 130%: при 200% числа 24-часового
циферблата наезжают друг на друга.

В форме ошибка поля — подсказка (`hint`) его узла: VoiceOver читает её вместе с полем. Текст
ошибки под строкой на Android — живая область, потому что объявлений там нет. Плашка над
кнопкой — живая область на обеих платформах.

### Чего нет и почему

| Нет | Почему |
|---|---|
| Use cases | Они бы только вызывали репозиторий. Логики на клиенте нет — деньги считает сервер (D6). У Flutter это conditional-рекомендация |
| DTO-копии моделей | Клиент не владеет контрактом и ничего не хранит; отдельные модели — только для тел ошибок. На сервере схемы есть (см. «Схемы API и домен») |
| Роутер | Один экран и нижний лист. Со вторым экраном появится go_router — его рекомендует Flutter |
| Локализация на несколько языков | Задание на русском; строки в одном месте, перевод добавляется позже |
| Crash reporting, аналитика | Нет продакшена, некуда отправлять |
| Локальная база | Нет офлайн-режима (см. «Сознательно не делаем» в decisions.md) |
| Сторонний UI-кит, свои шрифты | Material 3, своя тема и системные шрифты закрывают задачу (D11) |
| Отдельный интерфейс на Cupertino | Двойная работа ради одного экрана; платформенные различия закрыты адаптивными виджетами, значками и откликом на нажатие (D11) |
| Плавающая кнопка | Закрывала последнюю поездку; действие — кнопка с подписью в нижней панели (D11) |

## Сгенерированный код

`*.g.dart`, `*.freezed.dart`, `*.config.dart` коммитятся, чтобы `flutter run` работал сразу
после клонирования. В `.gitattributes` они помечены `linguist-generated=true` — GitHub
сворачивает их в диффах. CI запускает `build_runner` и падает, если сгенерированный код
расходится с закоммиченным.
