# Решения

Решения, которые задание оставляет открытыми. Каждое: что решили, почему, чем проверяется.
Если код начинает противоречить решению — в том же PR меняется либо код, либо этот файл.

## D1. День — по часовому поясу водителя

**Решение.** «День» — календарная дата в поясе водителя `Asia/Almaty`. Поездки за дату `D` —
это поездки, у которых начало попадает в `[D 00:00, D+1 00:00)` по Алматы.
Сервер хранит время в `timestamptz`, а границы дня переводит в UTC перед запросом.

**Почему.** Если группировать по дате в UTC, поездка в 01:00 по Алматы (20:00 UTC) уедет
в предыдущий день. Водитель считает смену по своим часам.

**Ловушка.** С 1 марта 2024 года весь Казахстан живёт по UTC+5. В устаревшей базе часовых
поясов `Asia/Almaty` всё ещё +06:00, и все границы дней съезжают на час.

**Проверка.**
- Тест: поездка в 00:30 по Алматы попадает в свою дату, а не в предыдущую.
- Тест-страж: смещение `Asia/Almaty` на 2026-10-01 равно +05:00. Отдельно на бэкенде (`zoneinfo`)
  и на клиенте (пакет `timezone`) — у них разные базы поясов.

## D2. Поездка через полночь

**Решение.** Поездка относится ко дню своего **начала**. Поездка 23:50–00:20 целиком
в предыдущем дне и не делится.

**Почему.** Поездка оплачивается один раз, делить сумму между днями нельзя. Правило «по началу»
однозначное и понятное водителю.

**Проверка.** Тест: поездка 23:50–00:20 есть в сводке своего дня и отсутствует в следующем.

## D3. Деньги — целые тенге

**Решение.** Суммы и комиссия — целые числа в тенге: `int` в Python и Dart, `integer` в Postgres.
Дробное значение в запросе (`2400.5`) — ошибка проверки, а не округление.

**Почему.** Тиыны на практике не используются, а `float` даёт ошибки округления при сложении.

## D4. Защита от дублей: `id` поездки как ключ

**Решение.** `id` поездки задаёт клиент, и это ключ идемпотентности. Уникальность обеспечивает
первичный ключ в базе: `INSERT … ON CONFLICT (id) DO NOTHING`, а не «сначала SELECT, потом INSERT».

| Ситуация | Ответ |
|---|---|
| Новый `id` | `201 Created` + поездка |
| Тот же `id`, те же данные | `200 OK` + уже сохранённая поездка |
| Тот же `id`, другие данные | `409 Conflict`, сохранённая поездка не меняется |

«Те же данные» сравниваются по смыслу: `08:10+05:00` и `03:10Z` — один и тот же момент.

**Почему.** В данных из задания у поездки уже есть `id`, так что второй механизм
(заголовок `Idempotency-Key`) не нужен. Проверка «SELECT, потом INSERT» ломается, когда два
одинаковых запроса приходят одновременно: оба не находят запись, оба вставляют.
`409` вместо тихой перезаписи — потому что расхождение данных под одним `id` означает ошибку
у клиента, и её нужно показать, а не спрятать.

**Проверка.**
- Повтор того же запроса → `200`, в базе одна запись.
- Тот же момент времени в другой записи смещения → `200`.
- Тот же `id` с другой суммой → `409`, сумма в базе прежняя.
- 20 одновременных одинаковых запросов → ровно одна запись, ровно один ответ `201`.
  Тест идёт на настоящем Postgres (`testcontainers`): на моках гонку не воспроизвести.

## D5. Проверка данных

**Решение.** Кроме двух проверок из задания (сумма > 0, окончание позже начала):

| Поле | Правило |
|---|---|
| `id` | непустая строка до 64 символов: латиница, цифры, `-`, `_` |
| `start`, `end` | ISO 8601 **со смещением**; время без смещения отклоняется |
| `amount` | целое, > 0 и не больше 2 147 483 647 (предел `integer` в Postgres) |
| `commission` | целое, от 0 до `amount` включительно |
| `payment` | `cash` или `card` |
| лишние поля | отклоняются |

Ошибки проверки — `422` с указанием поля, чтобы клиент показал ошибку под нужным полем формы.

**Почему.** Время без смещения нельзя однозначно отнести к дню (см. D1). Комиссия больше суммы
даст отрицательное «на руки». Сумма больше 2 147 483 647 не поместится в `integer`, и клиент
получил бы `500` вместо `422`.

## D6. Сводку считает только сервер

**Решение.** Клиент показывает сводку, которую вернул сервер, и сам её не пересчитывает.
На сервере сводка считается чистой функцией `summarize(trips)` из того же списка поездок,
который уходит в ответе.

**Почему.** Два места, где считаются деньги, рано или поздно разойдутся, и у части
пользователей окажется «неверная сумма». Сводка и список из одного запроса не могут
противоречить друг другу.

**Проверка.** Тесты `summarize`: пример из задания, пустой день, свойства на случайных данных
(наличные + карта = выручка; на руки = выручка − комиссия; число поездок = длина списка).

## D7. Повторы на клиенте

**Решение.**
- `id` новой поездки генерируется при открытии формы и хранится в состоянии блока. Это UUIDv7:
  он упорядочен по времени, поэтому индекс по первичному ключу растёт по порядку.
  Повторная отправка той же формы идёт с тем же `id`.
- Повтор — только для временных ошибок (нет связи, таймаут, 5xx). `409` и `422` не повторяются.
- Кнопка отправки не шлёт второй запрос, пока идёт первый (`droppable()`).

**Почему.** Самый опасный случай — запрос дошёл, а ответ потерялся. Если при повторе
сгенерировать новый `id`, сервер честно создаст вторую поездку. Защита на сервере (D4)
работает, только если клиент повторяет тот же `id`.

## D8. Один запрос на день

**Решение.** `GET /api/v1/days/{date}` отдаёт сводку и список поездок вместе.

**Почему.** Это один экран, значит один запрос: меньше задержка на мобильной сети, а сводка
и список берутся из одного снимка данных (см. D6).

## D9. Один водитель, без авторизации

**Решение.** Сервис работает с поездками одного водителя. Пояс водителя задаётся настройкой
`DRIVER_TZ` (по умолчанию `Asia/Almaty`).

**Почему.** Авторизации и нескольких водителей в задании нет. Добавить `driver_id` позже —
одно поле в таблице и в пути API.

## D10. Хранилище: Postgres, SQL без ORM

**Решение.** Postgres 18, асинхронный psycopg 3 с пулом соединений, два-три SQL-запроса руками.
Схема — один `schema.sql`,
применяется при старте. Начальные данные из `data/trips.json` загружаются через ту же функцию
сохранения, поэтому повторный запуск не плодит дубли.

**Почему.** Защита от дублей держится на уникальном ключе и `ON CONFLICT` — это должно быть
видно в коде, а не спрятано в ORM. Для одной таблицы Alembic и ORM избыточны.

## D11. Интерфейс: Material 3 и адаптивное поведение

**Решение.** Material 3 со своей минимальной темой: один цвет-основа, светлая и тёмная версии,
системные шрифты. Один интерфейс для iOS и Android; платформенные различия закрываются
адаптивными виджетами — выбор даты и времени, диалоги, индикаторы. Подробности —
в [architecture.md](architecture.md#интерфейс).

**Почему.**
- У водителей такси в основном Android, а там Material — родной стиль. На iOS Flutter сам
  подставляет SF Pro, свайп назад и пружинящую прокрутку.
- Отдельная дизайн-система или сторонний UI-кит для одного экрана — лишняя зависимость.
  Тема в одном месте даёт ту же согласованность.
- Второй интерфейс на Cupertino — двойная работа и двойные тесты. Пользователь замечает
  различия в выборе даты, диалогах и жестах — их и адаптируем.
- Тёмная тема по системной настройке — потому что смены бывают ночные.

**Проверка.** Виджет-тесты экрана дня и формы в светлой и тёмной теме и при масштабе шрифта
200%: без ошибок переполнения.

## D12. Адрес API и демо: бэкенд в интернете

**Решение.** Бэкенд разворачивается на хостинге с HTTPS. APK в GitHub Releases собирается
с этим адресом, поэтому работает на любом телефоне без настройки. Адрес API задаётся при сборке
(`--dart-define-from-file`), а не в коде: для эмулятора, симулятора и телефона в локальной сети
есть свои файлы. Как это устроено — в [architecture.md](architecture.md#окружения).

**Почему.** Проверяющие ставят APK на свой телефон, а он не достучится до `localhost`
разработчика. Демо-сборка с фейковым репозиторием тоже работала бы без сети, но не показала бы
сервер: границы дня, проверку данных и защиту от дублей. Бэкенд в интернете показывает всё
от телефона до базы.

**Риски.**
- Бесплатный хостинг может «засыпать», и первый запрос идёт долго. Экран показывает загрузку,
  а при таймауте — ошибку с кнопкой «Повторить».
- API открыт без авторизации (D9), и кто угодно может добавить поездку. Для демо это приемлемо;
  данные восстанавливаются перезапуском с чистой базой.

**Проверка.** APK из Releases на телефоне вне домашней сети показывает сводку за 01.10.2026
из задания.

## Сознательно не делаем

Правила ниже звучат разумно, но в задании их нет, и они зависят от бизнеса. В реальной
команде я бы уточнил их у продакта, а не придумывал.

- **Пересечение поездок по времени.** Две поездки одного водителя в одно время — скорее ошибка,
  но бывают попутные заказы.
- **Максимальная длительность поездки.** Непонятно, где граница: 6 часов? 24?
- **Офлайн-очередь на клиенте.** Повтор с тем же `id` (D7) закрывает потерю ответа;
  полноценная очередь без сети — отдельная задача.
- **Редактирование и удаление поездок.** Не просили.
